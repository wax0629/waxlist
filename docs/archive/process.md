# 协作与文档流程（轻量）

> 给个人 / 小团队用的「够用就好」规范，不是大厂全套流程。

---

## 1. 我们现在的流程算不算规范？

**算，而且对 v0.1 这种产品很合适。**

实际走过的是：

```text
产品构思 / 边界（product-concept, thinking-map）
  → 信息架构 / 模块专篇（IA, underground）
  → 技术决策 A–F（tech-decisions）
  → 可开发规格（spec-v0.1）
  → 编码切片（UI → API → YouTube → Agent → 抛光）
  → 用真 key 验收三条路径
```

这不是「没文档就写代码」，而是：

| 阶段 | 文档职责 | 代码职责 |
|------|----------|----------|
| 想清楚 | 定位、非目标、一站两页、不做荐专主路径 | 无 |
| 能开工 | 选型、API 草图、DoD | 无 / 骨架 |
| 做出来 | 随实现改 spec / README | 主战场 |
| 记后话 | **ideas-backlog**（想法）、以后再升规格 | 不立刻做 |

常见误区有两个：

1. **文档写到完美再动代码** → 对 Agent/检索类产品过慢，很多问题只有接真 API 才暴露。  
2. **零文档纯 vibe coding** → 边界会漂（编曲、荐专、灰产下载一锅炖）。

我们走的是中间路线：**先锁边界与 v0.1 切口，再切片实现，用验收路径校正。** 这就是个人作品 / 早期产品的常规做法。

---

## 2. 文档怎么分层（维护什么）

| 层级 | 文档 | 何时改 |
|------|------|--------|
| **北极星** | `product-concept.md` | 定位、用户、原则变了才改 |
| **地图** | `thinking-map.md`、`information-architecture.md` | 站点结构、主线/支线关系变了 |
| **决策日志** | `tech-decisions.md` | 定下或推翻技术选择时追加 |
| **当前版本契约** | `spec-v0.x.md` | **开工前写**；做完勾 DoD；大改同步 |
| **操作说明** | `youtube-api-setup.md`、README | 环境、怎么跑、怎么演示 |
| **想法池** | `ideas-backlog.md` | **随时记**；不自动进开发 |
| **流程** | 本文 `process.md` | 协作方式变了再改 |

原则：

- **想法 ≠ 需求**：先记 backlog，升格到 spec 才开工。  
- **spec 只覆盖当前版本**：v0.2 另开 `spec-v0.2.md`，别把 v0.1 写成百科。  
- **代码与 spec 冲突时**：要么改代码，要么改 spec，并在 PR/提交说明里写一句为什么。

## 3. 建议的日常节奏

### 有新功能冲动时

```text
1. 写进 ideas-backlog.md（一句话 + 为什么 + 大概版本）
2. 若要做：从 backlog 勾到「下一版候选」
3. 开/更新 spec-v0.x（用户故事 + 非目标 + DoD）
4. 按切片写代码
5. 勾 DoD，必要时回写 product 文档
```

### 每次开工前 2 分钟

- 主线还是「找 beat 短名单」吗？  
- 这次改动会不会把荐专/编曲/灰产拖进来？会 → 放 backlog 或明确拒绝。  

### 不必维护的（现阶段）

- 完整 UML / 详尽 OpenAPI（API 少时 spec 草图够用）  
- 每周状态会纪要  
- 强 ADR 编号体系（tech-decisions 表格式已够）

---

## 4. 和「先维护几份文档」的关系

| 你已有 | 作用 |
|--------|------|
| 产品构思、思路图、IA | 回答「做什么 / 不做什么」 |
| tech-decisions | 回答「用什么做」 |
| spec-v0.1 | 回答「这版做到哪算完」 |
| ideas-backlog（新建） | 回答「以后可能做什么」 |

所以：**不是缺文档，而是要把「后续想法」从主规格里拆出去**，避免再次 scope 膨胀。  
主规格保持薄；想法堆在 backlog；真要做再写下一版 spec。

---

## 5. 版本升级时最小文档动作

发 v0.2 之前至少：

1. `ideas-backlog` 里勾选本版要做的条目  
2. 新建 `spec-v0.2.md`（或从 v0.1 复制改范围）  
3. 若架构变了：补一行 `tech-decisions`  
4. README「当前状态 / 演示路径」更新  

不需要重写全部产品文档。
